## Phase 2 — Critical security hardening

- [x] `generalLimiter` was defined (`server/src/middleware/rateLimiters.ts:99`) but never mounted. Fixed: single `app.use('/api/v1', generalLimiter, routes)` in `server/src/index.ts` — a floor rate limit for every route, root-cause fix instead of 15 point edits. Routes with tighter needs keep layering their own stricter limiter on top.
- [x] No CSRF protection on `/auth/refresh` / `/auth/logout` (cookie-only auth, `sameSite:'none'` in production). Fixed: `requireTrustedOrigin` middleware in `server/src/routes/auth.ts` checks `Origin`/`Referer` against the same allow-list CORS uses (extracted to `server/src/lib/allowedOrigins.ts` so it's defined once, not duplicated).
- [x] Default import password `'school123'` — turned out to be an editable, pre-filled UI default (`client/.../ImportExport.tsx`), not a hidden hardcoded value, so severity was lower than first assumed. Real bug found while fixing it: the server validation `if (defaultPassword && defaultPassword.length < 8)` skipped entirely when `defaultPassword` was `''` (falsy), so `bcrypt.hash('', 10)` could create accounts with an **empty password**. Fixed both `/import/apply` and `/import/apply-teachers` to `if (!defaultPassword || defaultPassword.length < 8)`, and removed the `'school123'` fallback/pre-fill on both ends so admins must type a real password. *Deferred, bigger scope, own PR: true per-user random passwords + forced reset-on-first-login (needs a schema migration).*
- [x] Silent `catch {}` blocks in `server/src/routes/schools.ts:28,44` now log via `pino` before responding 500.
- [x] `xlsx@0.18.5` (client-only, confined to `ImportExport.tsx`) had unpatched CVEs — npm registry is frozen at 0.18.5, SheetJS ships patches only via their own CDN now. Verified `https://cdn.sheetjs.com/xlsx-0.20.3/xlsx-0.20.3.tgz` resolves (curl 200) and is the latest available (probed 0.20.4–0.21.0, all 404). Pinned `client/package.json` to that tarball URL — same public API, `npm audit` no longer lists xlsx, tests/build green.

## Phase 9 — Deeper security pass (OWASP sweep) + manual browser verification

Requested after Phase 1–8 landed: a systematic OWASP Top 10 review (not just re-checking the phases above) plus actually driving the app in a browser instead of only trusting automated tests.

**Manual browser verification** — ran the real app (client + server on non-default ports, pointed at the existing seeded dev DB) and clicked through login (both the dev-autologin shortcut and a real email/password submit), the schedule grid → SlotPanel → attendance marking, and creating a payment via the Finance dashboard. All worked end-to-end with real data; the response headers on a live request confirmed the Phase 2 `generalLimiter` fix is actually active (`ratelimit-limit: 200` on a route — `PATCH /students/:id` — that had zero rate limiting before this PR). Also found, while testing: the local `eduschool_test` database (used only by `npm run test:integration`, separate from the dev DB) was 4 migrations behind, which made ~670 of 941 integration tests fail with a missing-column error — a local environment gap, not a code bug (CI always starts from a fresh, fully-migrated DB, so this never affected CI). Ran `prisma migrate deploy` against it; full integration suite (941 tests) now passes.

**OWASP findings, verified against source before fixing:**
- [x] **A01 Broken Access Control** — `users.ts` `GET /` and `GET /:id` had `authenticate` but no `requirePermission`, so any authenticated STUDENT/TEACHER could list every user in their school including `staffProfile.salaryRate` and `studentProfile.credits/moneyBalance/notes`. Fixing this by reusing `users:manage` would have broken real ADMIN pages (Teachers/Schedule/GroupDetail all call this endpoint, and ADMIN doesn't hold `users:manage` — only OWNER/SUPERADMIN do). Added a new `users:read` permission instead, granted to SUPERADMIN/OWNER/ADMIN, matching this codebase's existing read/write-per-resource convention (`finance:read` vs `finance:write`, etc.) — purely additive, no existing grant touched.
- [x] **A01 Broken Access Control (defense-in-depth, narrower than first assumed)** — `credits.ts`'s idempotency-replay branch looked up the profile to return by the **replay request's own body** (`studentProfileId`, unscoped by `schoolId`) instead of the original logged operation's profile. The initial read of this (mine, before tracing the full middleware chain) assumed a simple "replay with a different id" attack, which isn't actually reachable: `dbIdempotency` middleware runs first, hashes the *entire* request body, and returns 409 on any mismatch — and on an exact replay it serves the cached response directly, never calling into this code at all. The only way to actually reach `credits.ts`'s own branch with a body that disagrees with the original is `dbIdempotency`'s stale-`IN_PROGRESS` reclaim path (>5 min, i.e. the original request crashed mid-flight) — and that path is itself scoped to the caller's *own* `schoolId`, so this was never cross-tenant. Still a real bug (a same-school user could, in that narrow crash-recovery window, read a different student's credit balance by id-guessing), and the fix (use `existingLog.studentProfileId`, the authoritative source, instead of trusting the request body) is correct and strictly safer either way — just documenting the real severity instead of the scarier first read.
- [x] **A06 Vulnerable Dependencies** — server: `multer` → 2.2.0, `sharp` → 0.35.3 (both direct deps with real CVEs — DoS and libvips issues respectively, both used in the upload path). `npm audit fix` (non-forced) cleared most transitive issues. The one remaining critical (`tar`, via `@mapbox/node-pre-gyp`, install-time only) had no fix via semver ranges even with `--force`, so pinned it directly with a `package.json` `overrides` entry; verified `bcrypt`'s native binding (which depends on this install chain) still works. Client: `axios` → 1.19.0 (direct dep, the actual HTTP client — CVE list included prototype-pollution credential theft), `npm audit fix` cleared vite/ws/lodash/js-yaml/etc. `react-router` moved from 12 vulnerable versions down to one (a React Server Components CSRF bypass) that doesn't apply — this app is a client-only SPA, no RSC usage anywhere. Fixing that specific CVE requires a major version bump (7→8); **deliberately deferred** — a core routing library major bump needs its own dedicated PR with real regression testing, not a rushed change at the tail of an already-large PR. Remaining after all this: one low-severity `esbuild` issue nested in `tsx`'s own dependency tree (dev-only, no fix published yet).
- [x] **A09 Security Logging** — `admin.ts`'s audit-log UI already advertised `LOGIN_FAILED`/`RATE_LIMIT_TRIGGERED`/`TOKEN_REUSE_DETECTED`/`PERMISSION_DENIED` as filterable event types, but `logSecurityEvent()` was never actually called for any of them — filtering by those types silently returned nothing. Wired all four: `auth.ts` login (both "no matching account" and "wrong password" branches), `requirePermission.ts`'s 403 path, `rateLimiters.ts`'s 429 handler (previously had no `handler` at all, so a rate-limit trip left zero trace anywhere), and `auth.ts`'s refresh-token-reuse branch (upgraded from a bare pino line to the full audit-logged event).
  - Self-caught bug: the first version of the `requirePermission.ts`/`rateLimiters.ts` wiring called `logSecurityEvent()` fire-and-forget (`void ...`, not awaited) to avoid adding latency to the reject path. That looked harmless, but it caused a real, reproducible integration-test deadlock: a 403 response returns before its unawaited `ScheduleActionLog` INSERT finishes, and if the *next* test's `beforeEach` → `cleanDb()` TRUNCATE (which includes that table) starts before the insert lands, Postgres deadlocks the two. Confirmed by tracing the exact relations in the deadlock error (`ScheduleActionLog` vs `StudentGroup`, an FK target) and reproducing it consistently, then fixing it by making both call sites `await` the write — worth the small latency cost on an already-rare rejection path. Re-verified: full 941-test integration suite is clean after the fix. First assumed (wrongly) that this was pre-existing Windows/Postgres flakiness already described in `TESTING_STRATEGY.md` — traced it properly instead of accepting that explanation at face value.
- [x] **A05 Security Misconfiguration** — fixed the worst offender: `settings.ts`'s `clear-all-data` 500 handler was forwarding raw Prisma `error.meta` (can contain column/constraint names) straight to the client response. Now logs full detail server-side only, returns a generic message.
- [ ] **A05, deferred** — ~20 other route files forward `err.message` verbatim in their generic 500 fallback (not the controlled business-logic error paths, which already return fixed messages). Lower severity than the clear-all-data case — no `meta`/`code` leakage, just error text — but still not great practice. Left as backlog rather than a rushed mechanical sweep across 20 files; same reasoning as the Phase 3 zod scoping decision.
- No findings: A02 (bcrypt cost factor 10 consistent, password/token fields excluded from queries by default), A03 (all raw SQL parameterized, no `eval`), A04 (destructive endpoints have real guardrails), A07 (no account enumeration, refresh rotation + reuse detection already solid), A08 (no unusual install-time scripts), A10 (the one user-controllable outbound URL — webhooks — already has DNS-rebinding protection).

## Phase 10 — Full audit post-Railway-migration (2026-08-09)

Requested after the Render+Vercel+Supabase → Railway migration (2026-08-08) found six bugs reactively in one session (see `AUDIT_BRIEF_2026-08-08.md`): a systematic, evidence-based pass across all 40 route files, business logic vs. `AI_SCHEDULE_HANDOFF.md`/`SCHEDULE_LIFECYCLE_RFC.md`, performance, config/infra, live browser walkthrough (5 roles), and a financial-integrity race test — done via parallel Explore-agent audits + live curl/browser verification against a local DB seeded with two real multi-role schools, not just code review.

**Multi-tenancy & authorization** (§3 of the brief) — 274 route handlers read across the 4 audit batches (route/page/test inventory corrected: 40 route files not ~39). Zero cross-tenant `schoolId` leaks found beyond one write-path bug. Fixed:
- [x] **Critical: `importexport.ts` teacher-CSV import — cross-tenant write IDOR.** `POST /import/preview-teachers` and `POST /import/apply-teachers` looked up existing users by email with no `schoolId` filter — an OWNER in School A importing a CSV containing a real teacher's email from School B would see (preview) or **overwrite** (`apply`, via the "update" resolution) that School-B user's name/phone. Fixed by adding `schoolId` to both lookups.
- [x] **`groups.ts POST /` — cross-tenant `GroupMembership` IDOR.** Initial `studentIds` on group creation skipped `assertStudentsBelongToSchool` (present on the sibling `POST /:id/students`) — a School-A admin could enroll a School-B student into a School-A group. Fixed.
- [x] **9 role-matrix gaps** (TEACHER/STUDENT reaching OWNER/ADMIN-only data, or ADMIN reaching OWNER-only mutations) across `groups.ts` (2 missing role checks), `parent.ts`, `importexport.ts` exports (student/teacher/schedule CSV — teacher export leaked `salaryRate`), `settings.ts` (`GET /finance` had zero role gate), `users.ts` (`PATCH /:id/staff-profile` let ADMIN change `salaryRate` via `schedule:write`, bypassing the OWNER-only gate `salary.ts` correctly enforces for the same field) — all fixed with the narrowest correct permission, matched to sibling routes already doing it right.
- [x] **TEACHER could act on any session in the school, not just their own** (`scheduleAttendance.routes.ts`, `scheduleSessions.routes.ts` `PATCH /session/:id/status`) — `attendance:write`/`session:write` correctly restrict to staff roles but never checked the session belonged to the calling teacher. New `assertTeacherOwnsSession()` helper closes this; no-op for OWNER/ADMIN. Live-verified with two real teacher accounts.
- [x] **4 GET routes with zero permission middleware** (schedule blocks list, session-for-date, session logs, session roster) — any authenticated role including STUDENT could read cross-student credits/notes/audit trail. Gated with `students:read`.
- [ ] **Left open, needs owner decision — not fixed:** three ADMIN-scope findings (`schools.ts PUT /current/me`, `settings.ts PATCH /general`, `students.ts` payment-cancel) grant ADMIN a capability the audit brief's stated matrix reserves for OWNER, but each is explicitly commented in the code as an intentional design choice ("OWNER/ADMIN", "front-desk task"). Silently overriding a documented product decision on an unverified doc-vs-code conflict was judged riskier than leaving it — flagged for the owner to resolve, not treated as a bug.
- [x] **Live IDOR probing** (not just code review) — logged in as STUDENT/TEACHER/ADMIN across two real seeded schools (`adiltest`, `hunya-shkola`) via curl, confirmed each fix's before/after behavior (403 where previously 200, cross-tenant leak now empty/blocked) with real request/response pairs.

**Financial & data integrity** (§4) — raced two genuinely concurrent `POST /session/submit-attendance` requests (different idempotency keys, same session/student) against the live server: one succeeded, the other correctly rejected with `ATTENDANCE_FINALIZED`; DB confirmed exactly one `Attendance`/`LessonCreditLog` row and a single credit deduction — no double-deduction under a real race. Cancel-guard re-verified across all 9 code paths that can cancel/invalidate a session or block: every one correctly blocks on `creditDeducted`/existing-attendance and none auto-refunds (confirmed live: attempting to cancel a just-finalized session returned "transition not allowed"). One latent-but-unreachable gap noted: `invalidateSession()` skips the `creditDeducted` guard but isn't wired to any route today.

**Business logic vs. docs** (§5) — two real bugs found and fixed:
- [x] **CSV student import (`paused=true`) never created a `StudentFreeze` row** — only wrote the legacy `StudentProfile.isFrozen` cache field, so an imported "frozen" student still had credit deducted on attendance (the real gate only checks live `StudentFreeze`, per this doc's own source-of-truth rule). Fixed: import now creates an open-ended `PERIOD` freeze in the same transaction.
- [x] **`PATCH /schedule/enrollment/:id/approve/:studentProfileId` had no group-capacity check**, unlike its siblings `/add` and bulk-`/students` — approving a waitlisted student could silently overbook a group. Fixed with the same `effectiveCap` check.
- Confirmed correct (no fix needed): `StudentFreeze` is the live read-side gate everywhere except the import bug above; `LessonSession.version` optimistic-lock is checked on every endpoint that accepts it; salary already-paid/double-pay/adjustment-after-payment are all correctly guarded (unique constraints + explicit 409s); legacy `enrolledBlocks` doesn't exist anywhere in the codebase (already fully migrated to `GroupMembership`).

**Performance** (§7) — DB too small locally (559 sessions) for `EXPLAIN ANALYZE` to be meaningful; reasoned from the composite-index list instead. Fixed 3 queries that filtered `schoolId` only through a nested relation instead of the indexed top-level column (`scheduleDashboard.routes.ts` ×2, `scheduleBlocks.routes.ts` `GET /teacher`) — not a data leak, but defeats `@@index([schoolId,...])` and forces a cross-tenant scan at 50-school scale. Fixed missing `useMemo` on `Students.tsx`'s filter/sort (reruns a full 3000-row `localeCompare` sort on unrelated re-renders). Confirmed the lint-flagged `sched` missing-dependency warnings across 5 schedule grid components are **false positives** — `sched` is intentionally unstable-by-reference so per-student clicks don't repaint the whole grid; adding it to deps would be the regression, not the fix. Left open (flagged, not fixed — needs its own scoped change): `analytics.ts`'s `dashboardStats()` pulls an unbounded 30-day attendance query into Node for JS-side aggregation instead of a DB-side `groupBy`.

**Config/infra** (§9):
- [x] `RegisterSchool.tsx:376` — same dummy-Google-client-ID fallback as `Login.tsx`, now fixed identically: skip loading the Google SDK entirely (not just the button) when `VITE_GOOGLE_CLIENT_ID` is unset, instead of loading it with a fake ID that fails every attempt with a confusing 403.

- [x] **`invites.ts`'s refresh cookie hardcoded `sameSite:'lax'`**, unlike `auth.ts`'s dynamic `none`/`lax` — in production (cross-origin Railway client/API) this cookie would be silently dropped by the browser, breaking the just-accepted-invite auto-login. Fixed to match `auth.ts`.
- [x] `render.yaml` and `client/vercel.json` removed (dead config since the Railway migration); stale Render/Vercel wording fixed in `DEPLOYMENT.md` and an `auth.ts` code comment.
- [ ] **Owner checklist (can't verify without Railway dashboard/CLI access):** confirm `DISABLE_ERD=true` is actually set as a Railway env var on the live API service (present in `pr-checks.yml`, that doesn't prove it's set on Railway); confirm Postgres daily backups are enabled on the Railway Pro plan and perform one real test-restore (`server/scripts/verify-backup.ts` exists for this — run it against a restored copy).

**Tests** — full suite run clean after all fixes: server 24 unit (540 tests) + 76 integration (943 tests) suites, client build + lint (0 errors, 43 pre-existing warnings) + 18 test files (207 tests). Added `teacherOwnership.test.ts` (6 cases) and `auditFixes2026-08-09.test.ts` (cross-tenant IDOR regressions for the two critical findings above).
